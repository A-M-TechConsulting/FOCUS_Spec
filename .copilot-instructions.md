# Copilot Instructions: Creating FOCUS Conformance Rules

## Overview
This guide provides streamlined instructions for AI-assisted generation of conformance rules for FOCUS specification columns and attributes. Follow the established patterns documented in `/guidelines/normative-requirements-guidelines.md` and reference existing conformance rules in `/specification/conformance/conformance_rules/`.

## Rule Naming Convention

### For Columns
Format: `{ColumnName}-C-{SequenceId}-{Classification}`
- **ColumnName**: Pascal case column identifier (e.g., `BilledCost`)
- **C**: Entity type (Column)
- **SequenceId**: 3-digit sequence starting from 001 
- **Classification**: M (Mandatory), O (Optional), C (Conditional)

Examples:
- `BilledCost-C-001-M` (Mandatory presence rule)
- `AvailabilityZone-C-001-C` (Conditional presence rule)

### For Attributes
Format: `{AttributeName}-A-{SequenceId}-{Classification}`
- **AttributeName**: Pascal case attribute identifier (e.g., `CurrencyCodeFormat`)
- **A**: Entity type (Attribute)
- **SequenceId**: 3-digit sequence starting from 001
- **Classification**: M (Mandatory), O (Optional), C (Conditional)

Examples:
- `CurrencyCodeFormat-A-001-M` (Mandatory currency format rule)
- `DateTimeFormat-A-001-M` (Mandatory datetime format rule)

## Rule Structure Components

### Required Fields
- **Function**: `Composite|Presence|Type|Format|Validation`
- **Reference**: Column or attribute name
- **EntityType**: `Column|Attribute`
- **CRVersionIntroduced**: Current FOCUS version (e.g., "1.2")
- **Status**: `Active`
- **ApplicabilityCriteria**: Array of feature flags (empty `[]` for universal rules)
- **Type**: `Static|Dynamic`
- **ValidationCriteria**: Complete validation object

### ValidationCriteria Structure
```json
{
  "MustSatisfy": "Human-readable requirement description",
  "Keyword": "MUST|SHOULD|RECOMMENDED|MAY",
  "Requirement": {
    "CheckFunction": "Function name",
    "ColumnName": "Column name", // For column rules
    "AttributeName": "Attribute name", // For attribute rules
    // Additional function-specific parameters
  },
  "Condition": {}, // Empty for unconditional rules
  "Dependencies": [] // Array of dependent rule IDs
}
```

## Common Rule Functions

### 1. Composite Rule (Always -000-M)
```json
"Function": "Composite",
"Type": "Static",
"Requirement": {
  "CheckFunction": "AND",
  "Items": [
    {"CheckFunction": "CheckConformanceRule", "ConformanceRuleId": "{EntityName}-{EntityType}-001-M"},
    {"CheckFunction": "CheckConformanceRule", "ConformanceRuleId": "{EntityName}-{EntityType}-002-M"}
  ]
}
```

### 2. Presence Rules (For Columns)
```json
"Function": "Presence",
"Type": "Static",
"Requirement": {
  "CheckFunction": "ColumnPresent",
  "ColumnName": "{ColumnName}"
}
```

### 3. Type Rules
```json
"Function": "Type", 
"Type": "Static",
"Requirement": {
  "CheckFunction": "TypeDecimal|TypeString|TypeDateTime",
  "ColumnName": "{ColumnName}" // For column rules
}
```

### 4. Format Rules
```json
"Function": "Format",
"Type": "Static", 
"Requirement": {
  "CheckFunction": "FormatNumeric|FormatString|FormatDateTime|FormatKeyValue|FormatCurrency",
  "ColumnName": "{ColumnName}" // For column rules
}
```

### 5. Validation Rules
```json
"Function": "Validation",
"Type": "Static|Dynamic",
"Requirement": {
  "CheckFunction": "CheckNotValue|CheckValue|CheckRange",
  "ColumnName": "{ColumnName}", // For column rules
  "Value": null|0|"specific_value"
}
```

### 6. Attribute Validation Rules
```json
"Function": "Validation",
"Type": "Static|Dynamic",
"Requirement": {
  // Often empty {} for complex attribute requirements
  // that require external validation logic
}
```

## Step-by-Step Workflow

### For Columns

### 1. Analyze Column Definition
Read the column's markdown file in `/specification/columns/{columnname}.md` to extract:
- **Column ID** and **Display Name**
- **Content Constraints** table (data type, feature level, nullability)
- **Normative requirements** (bullet points starting with MUST/SHOULD/MAY)

### 2. Determine Rule Classification
Based on feature level from Content Constraints:
- **Mandatory**: Rules classified as M
- **Conditional**: Rules classified as C 
- **Optional/Recommended**: Rules classified as O

### 3. Map Requirements to Rule Types
Following the order in `/guidelines/normative-requirements-guidelines.md`:

#### Technical Requirements (Order: 1-6)
1. **Presence** (001): Always first rule after composite
2. **Data Type** (002): Based on "Data type" from constraints
3. **Value Format** (003): Based on "Value format" from constraints  
4. **Nullability** (004): Based on "Allows nulls" and null-related requirements
5. **Values/Ranges** (005+): From MUST be valid/specific value requirements
6. **Column Relationships** (N): Cross-column consistency requirements

#### Business Requirements (Order: 7+)
7. **Unit/Denomination** (N): Currency/unit requirements
8. **Uniqueness** (N): Unique identifier requirements
9. **Fallback/Substitute** (N): Alternative value rules
10. **External Relationships** (N): Invoice/billing system alignment
11. **Cost Validation** (N): Formula-based validation rules
12. **Cost Calculation** (N): Complex calculation requirements

### 4. Generate JSON Structure
Create conformance rule file at:
- **Columns**: `/specification/conformance/conformance_rules/columns/{columnname}.json`
- **Attributes**: `/specification/conformance/conformance_rules/attributes/{attributename}.json`

#### Standard Pattern for Most Columns:
```json
{
  "{ColumnName}-C-000-M": {
    "Function": "Composite",
    "Reference": "{ColumnName}",
    "EntityType": "Column",
    "Notes": "",
    "CRVersionIntroduced": "1.2",
    "Status": "Active", 
    "ApplicabilityCriteria": [],
    "Type": "Static",
    "ValidationCriteria": {
      "MustSatisfy": "",
      "Keyword": "MUST",
      "Requirement": {
        "CheckFunction": "AND",
        "Items": [
          {"CheckFunction": "CheckConformanceRule", "ConformanceRuleId": "{ColumnName}-C-001-M"},
          {"CheckFunction": "CheckConformanceRule", "ConformanceRuleId": "{ColumnName}-C-002-M"}
          // Add all individual rule references
        ]
      },
      "Condition": {},
      "Dependencies": []
    }
  }
  // Individual rules follow...
}
```

### For Attributes

### 1. Analyze Attribute Definition
Read the attribute's markdown file in `/specification/attributes/{attributename}.md` to extract:
- **Attribute ID** and **Attribute Name**
- **Description** and **Requirements** sections
- **Normative requirements** (bullet points starting with MUST/SHOULD/MAY)

### 2. Determine Rule Classification
Based on requirement language:
- **MUST** requirements: Rules classified as M
- **SHOULD** requirements: Rules classified as O
- **Conditional MUST**: Rules classified as C

### 3. Map Requirements to Rule Types
Attributes typically focus on:
- **Format validation** rules for data structure requirements
- **Value validation** rules for allowed values and formats
- **Cross-cutting** rules that apply to multiple columns

### 4. Generate JSON Structure
#### Standard Pattern for Most Attributes:
```json
{
  "{AttributeName}-A-000-M": {
    "Function": "Composite",
    "Reference": "{AttributeName}",
    "EntityType": "Attribute",
    "Notes": "",
    "CRVersionIntroduced": "1.2",
    "Status": "Active",
    "ApplicabilityCriteria": [],
    "Type": "Static",
    "ValidationCriteria": {
      "MustSatisfy": "",
      "Keyword": "MUST",
      "Requirement": {
        "CheckFunction": "AND",
        "Items": [
          {"CheckFunction": "CheckConformanceRule", "ConformanceRuleId": "{AttributeName}-A-001-M"},
          {"CheckFunction": "CheckConformanceRule", "ConformanceRuleId": "{AttributeName}-A-002-M"}
          // Add all individual rule references  
        ]
      },
      "Condition": {},
      "Dependencies": []
    }
  }
  // Individual rules follow...
}
```

### 5. Handle Special Cases

#### Conditional Columns
- Set **ApplicabilityCriteria**: `["FEATURE_FLAG_NAME"]`
- First rule typically -001-C instead of -001-M
- Use **RECOMMENDED** keyword for presence when appropriate

#### Dynamic Rules  
- Set **Type**: `"Dynamic"`
- Leave **Requirement** as empty object `{}`
- Used for complex business logic requiring external validation

#### Complex Conditions
- Use nested conditional structure from guidelines
- Reference dependent rules in **Dependencies** array

## Validation

### 1. Schema Validation
```bash
cd /specification/conformance
python build_cr_json.py
```

### 2. Manual Review Checklist
- [ ] Rule IDs follow naming convention
- [ ] Composite rule (000) references all individual rules
- [ ] Technical requirements ordered before business requirements
- [ ] MUST/SHOULD/MAY keywords align with feature level
- [ ] Dependencies correctly reference prerequisite rules
- [ ] ApplicabilityCriteria set for conditional features
- [ ] All required JSON schema fields present

### 3. Content Alignment
- [ ] Rules capture all normative requirements from column definition
- [ ] MustSatisfy descriptions match specification language
- [ ] Rule classification (M/O/C) aligns with feature level
- [ ] Cross-references to other columns properly handled
